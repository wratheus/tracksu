# Tracksu — правила выполнения одной части

Редакция 10 · 2026-09-04.

Очередь и статусы — [ROADMAP](../plan/ROADMAP.md); технический scope —
[детали этапов](../plan/DETAILS.md). Здесь единственный рабочий цикл, ограничения,
протокол коммитов и шаблон карточки. Не перечитывать всё при каждой задаче:
старт — разделы 1, 3–6; выбранные технические правила — 7–13; сдача — 12, 14–17.
Skills подключаются по [маршрутизатору](../standards/SKILLS.md), с пользовательским исключением tests.

## 1. Режим работы

Сейчас разрешена подготовка: чтение кода и референсов, уточнение архитектуры,
сценариев, задач и документов. Начало реализации конкретной части выбирается
отдельно. Наличие всей дорожной карты не означает запуск всех её этапов.

В реализации одновременно находится одна часть, например P09.1. Внутри неё
исполнитель самостоятельно делает необходимые локальные изменения, review diff,
проверку формата/analyzer и сборку по необходимости. Поведение и внешний вид
пользователь тестирует вручную. Подтверждение каждого переименования или метода
не требуется.

**Автотестами сейчас не занимаемся.** Не пишем/переписываем/запускаем тесты,
не добавляем mocks, test fixtures/harnesses, golden, coverage и тестовый CI.
В плане для этого есть отдельная отложенная часть T01. Она не является
подзадачей каждого рефакторинга и не блокирует перенос feature.

**Производительность здесь — конкретные обновления UI:** широкий `setState`,
перестройки больших поддеревьев, повторные emit, таймеры и запросы из build.
Профилирование, бенчмарки и обязательные измерения в текущий процесс не входят.

Часть должна завершаться проверяемым результатом: работающий сценарий,
совместимый контракт или подтверждённая сборка. «Перенести все модели»,
«переписать весь UI» и «сделать Clean Architecture» — слишком широкие задачи.

Обычная техническая сложность не меняет договорённый объём. Если обнаружена
новая продуктовая развилка, затронуты данные/подпись или требуется пересмотреть
выбранную архитектуру, сначала описываем конкретное решение и последствия.

## 3. Сначала описываем изменение поведения

У каждой задачи есть тип. Если типов несколько, выделяем их в проверяемые шаги.

| Тип | Что сохраняем | Что показываем в результате |
| --- | --- | --- |
| Структурный рефакторинг | Данные, пользовательский сценарий и наблюдаемое поведение | Эквивалентность до/после и новую границу ответственности |
| Исправление бага | Всё вне конкретной ошибки | Воспроизведение ошибки, ожидаемое поведение и проверку исправления |
| Изменение UX/дизайна | Согласованные данные и сценарии | Новый вид/поведение и проверку состояний экрана |
| Совместимость SDK/API | Договорённый продуктовый результат | Новую сборку или контракт, список неизбежных отличий |

Старое поведение не всегда правильное. Например, потерю последнего игрока
рейтинга нужно исправить; ошибочный цикл не становится ожидаемым поведением.
Если ожидание неочевидно, помечаем его как открытый вопрос до изменения.

Новый дизайн и перенос архитектуры могут идти внутри одной feature. Для
проверки сначала фиксируем сценарий и данные на простом представлении, затем
применяем UI kit и визуальные изменения. Это позволяет понять причину отличий.

## 4. Когда задача готова к началу

До первого изменения исходников карточка части должна содержать:

- Цель одним предложением и соответствующий ID из очереди P00–P15.
- Конкретный сценарий или технический результат, его начальное состояние.
- Границы: какие feature, контракты и платформы затрагиваются.
- Краткий список того, что остаётся за рамками этой части.
- Известный baseline: успешные проверки, подтверждённые ошибки, что не запускалось.
- Зависимости: предыдущие части, решения, примеры данных и доступные сборки.
- Критерии завершения и способ проверки каждого критерия.
- Способ возврата: код, route и отдельно состояние локальных данных.

Если нельзя объяснить результат без перечисления множества независимых
сценариев, задачу дробим. Размер diff сам по себе не определяет размер задачи:
сгенерированный файл может быть большим, а изменение одного storage key —
существенным для всех пользователей.

## 5. Рабочий цикл одной части

1. **Прочитать затронутый путь целиком.** Проследить событие пользователя,
   состояние, запрос, decoder, UI и освобождение ресурсов. Проверить git status
   и существующие пользовательские изменения.
2. **Зафиксировать исходную точку.** Сохранить команды и доступные результаты,
   примеры JSON, screenshots или описание бага от пользователя. Токены и
   приватные значения в эти материалы не попадают.
3. **Описать контракт.** Входы, выходы, ошибки, отмена, lifetime, сохранение
   content при refresh и ожидаемые различия старой/новой реализации.
4. **Описать ручную проверку.** Несколько конкретных действий и ожидаемый
   результат для пользователя. Автоматический тест для этого шага не пишем.
5. **Ввести новую реализацию или границу.** Порциями, сохраняя возможность
   проверить текущий шаг. Не переносить соседние feature заодно.
6. **Подключить потребителя.** Новый route/компонент использует новый контракт.
   Проверить diff/analyzer/сборку по scope и передать сценарий пользователю.
7. **Убрать заменённый путь.** После проверки usages удалить мёртвый код и
   временные адаптеры, больше не нужные этой части.
8. **Зафиксировать результат.** Технические проверки, изменения поведения,
   commit и результат ручной проверки пользователя, когда он получен. До него
   статус `awaiting_manual_check`; следующий шаг выбираем отдельно.

Рутинную связанную работу исполнитель завершает самостоятельно. Обнаруженный
посторонний дефект записывается в backlog с файлом и способом воспроизведения.
Если он блокирует текущий сценарий, описываем зависимость и выделяем минимальную
подзадачу, вместо незаметного расширения всего рефакторинга.

## 6. Как переносим старое приложение

Основной приём — постепенная замена feature. В переходный период старые экраны
и новые слои могут жить в одном приложении.

- Начинаем с узкой границы: repository interface или отдельный чистый widget.
  Старый потребитель можно временно подключить к новому repository через adapter.
- Domain и UI kit не импортируют legacy-классы. Преобразования старых моделей
  живут во временном adapter на внешней стороне архитектуры.
- У конкретного экрана в каждый момент один владелец состояния и один путь
  загрузки. Не запускаем старый Cubit и новый Bloc одновременно «для сравнения»
  на реальном API.
- Пользователь сравнивает старый и новый UI на сопоставимых данных. Для переключения при
  разработке достаточно локального wiring в composition root; отдельный
  сервис feature flags для миграции не нужен.
- У временного adapter/переключателя есть владелец, задача удаления и условие:
  «последний legacy consumer переведён». Комментария `TODO later` недостаточно.
- Сохраняем стабильные IDs, ruleset и маршрутный контекст. Не переносим
  mutable DTO из одного экрана в другой как источник состояния.
- Удаляем legacy-файлы после проверки всех consumers, а не потому, что новый
  экран один раз открылся. Возврат к старому коду остаётся возможным через Git.

Мы не перемещаем сначала весь `lib/src` в новые папки. Наличие каталогов
`domain/data/bloc/widgets` ещё не подтверждает разделение ответственности.

## 7. Правила Clean/DDD и зависимостей

| Слой | Отвечает за | Не должен содержать |
| --- | --- | --- |
| Domain | Понятия feature, инварианты, repository contracts, нужные use cases | Flutter widgets, Color, HTTP, JSON, secure storage и SDK plugins |
| Data | DTO, mapping, API/storage adapters, реализацию repository | Навигацию, UI-state и визуальное оформление |
| Presentation | Bloc, отображаемые состояния, views, локальные эффекты | Прямые HTTP/storage вызовы, разбор JSON и хранение client credentials |
| Design system | Tokens и переиспользуемое поведение UI-компонентов | Endpoints, feature repositories, User/Score DTO и session state |
| App | Bootstrap, DI, routes и сборку графа зависимостей | Бизнес-правила feature и универсальный глобальный state всего приложения |

Между feature используем узкие публичные контракты. Внутренние реализации
соседнего модуля не импортируем. Если два модуля используют Score, сначала
определяем владельца и общую семантику; похожие поля не всегда означают одну
сущность. Shared domain выделяется только при реальной общей ответственности.

Use case нужен для сценария или политики, которую стоит назвать и отдельно
проверять. Прокси-класс вокруг каждого вызова repository не обязателен.
Repository не превращается в универсальный CRUD с `dynamic`.

Domain сохраняет значения в естественных типах: ID, числа, время, nullable
данные. Цвета ранга, строки процентов и формат дат принадлежат presentation.
Отсутствующее значение и ноль различаются. Новые значения API не должны
автоматически падать на неизвестном enum или превращаться в ложные данные.

Файловая схема следует TSD, а не параллельному `lib/features/.../presentation`:
`XxxMain` — локальная сборка SourceImpl → RepositoryImpl → Bloc;
`widgets/screen.dart` — отображение и listeners; `bloc/` — состояние/события.
Общая инфраструктура создаётся в `registerDependencies` и передаётся через
`DepsContainer/DepsScope`. `_core/router` и `_core/dependencies` вправе импортировать
feature entry points для wiring, но domain/packages не импортируют эти фасады.
`tracksu_ui` не зависит от User/Score/session; `tracksu_models` не знает Flutter,
Dio или storage. Utils не становятся складом бизнес-логики.

### 7.1. Отдельная задача DI — P05.1

DI foundation выполняется до P06, не прячется внутри первого repository или
аналитики. Используем TSD `registerDependencies → DepsContainer → DepsScope`,
`AppMain` для root providers и `XxxMain` для локального wiring. Новые клиенты
добавляются в этот граф по мере реализации своих этапов.

Container не хранит весь UI-state и не передаётся в каждый Bloc. Через constructors
передаются только нужные interfaces; обращения к scope остаются в composition
layer. До регистрации записать владельца/lifetime, инициализацию и освобождение.
Не повторять bootstrap в build, не закрывать общий клиент из route, не маскировать
полусобранные зависимости nullable-полями. Bootstrap error/retry не создаёт второй
параллельный контейнер. Подробный scope и ручные критерии — в P05.1 плана.

## 8. Правила Bloc и состояния

Для маленького локального UI-state допустим State или узкий Cubit;
загрузка, сессия и feature-сценарии переходят на Bloc.
Сначала выписываем события и переходы, затем пишем Bloc. Владелец каждого
состояния определён: session, route или секция экрана.

По TSD: `bloc.dart` с `part 'event.dart' / 'state.dart'`, закрытые sealed
иерархии, feature-prefixed имена, exhaustive switch. `sequential()` — отправная
точка для упорядоченных команд, не универсальная политика: search/ruleset требуют
latest-wins, pagination — защиты от дублей. При разных transformers продумать
взаимодействие групп событий; не регистрировать base event и subtype так,
чтобы одно событие обрабатывалось дважды. `addError(error, stackTrace)` передаёт
ошибку в общий reporting path, который не дублирует уже показанное локальное сообщение.

- Начальная загрузка запускается один раз из lifecycle/composition root.
  `build` и builder селектора только отображают state.
- Initial loading, content, empty и initial failure различаются. Refresh и
  pagination имеют отдельный статус, чтобы не стирать уже показанный content.
- State неизменяемый; коллекции не мутируются после emit. Равенство соответствует
  данным, которые определяют поведение и отображение.
- Ошибка refresh оставляет content и возможность повторить действие. Ошибка
  pagination не превращает весь экран в полноэкранную ошибку.
- Для смены query/ruleset выбираем политику «последнее намерение побеждает»;
  для pagination исключаем дубли одной страницы; для повторного refresh задаём
  явно объединение либо игнорирование повторов.
- Запросы и ответы связываем с query/session: старый запрос не должен переписать
  данные нового фильтра или аккаунта. В ручной сценарий включаем быструю смену
  фильтра; автоматический race-test сейчас не добавляем.
- Способ отмены определяется возможностями выбранного транспорта. Независимо
  от него, устаревший результат не получает право менять текущий state.
- Navigation/snackbar/dialog выполняются на уровне UI effects/listener.
  Эффект не запускается повторно из-за rebuild, restore или подписки.
- Закрытие Bloc/route освобождает принадлежащие ему subscriptions/resources.
  Завершение запроса после закрытия не вызывает обновление закрытого владельца.

Переход на Bloc считается выполненным, когда исправлены ответственность,
состояния и обработка событий. Само наличие файлов `event/state/bloc` не
является критерием завершения.

## 9. Правила UI kit и компонентов

Начинаем с tokens и компонентов, нужных первой feature. Компонент получает
данные для отображения и callbacks; его можно открыть в каталоге без сети,
OAuth, router и глобального Bloc.

- Route/container связывает Bloc и view. View отображает понятную модель
  состояния; небольшие элементы получают только используемые значения.
- Собственные обёртки над Text/Container создаём, если они задают устойчивую
  семантику или поведение. Название `AppText` само по себе ничего не улучшает.
- Стандартные Flutter-компоненты и локальный UI-state допустимы. Не строим
  собственный layout/state framework ради единообразия файлов.
- Card, связанная со Score/Beatmap, сначала остаётся внутри feature. В UI kit
  выносим подтверждённые общие части: surface, thumbnail, badge, spacing.
- Сначала разделяем повторяющиеся ответственность и данные, затем обобщаем.
  Не создаём компонент с десятками флагов для всех различий старых карточек.
- Loading/empty/error, disabled, focus и длинный текст входят в контракт
  компонента. Передаём пользователю нужные text scaling/labels/touch сценарии.
- Навигация назад, активная вкладка и scroll state входят в UX-сценарий.
  Извлечение widget не должно незаметно создавать нового владельца состояния.

Для визуальных изменений описываем изменённые состояния и ожидаемый внешний
вид. Пользователь просматривает layout, текст и контраст. Golden и другие
визуальные автотесты отложены вместе с T01.

По UI skill: сначала public API `tracksu_ui`, semantic typography/theme,
локализация через `context.t` из `tracksu_l10n`; `Row/Column.spacing` и `Padding`
для отступов вместо пустых `SizedBox`. `SizedBox` для размеров/constraints и
`SizedBox.shrink()` допустимы. Tokens spacing берём из одной согласованной шкалы.
`AnimatedBlocBuilder` — необязательная анимация, не способ уменьшить rebuild.
Границы обновлений задаются владельцами состояния и узкими selectors/builders.

Локализация — критерий готовности каждого нового UI, не отдельный хвост после
рефакторинга всех экранов. P07.1 сначала вводит ARB/locale/fallback; затем feature
добавляет ключи и переводы всех согласованных языков, placeholders/plurals,
accessibility labels и locale-aware форматирование. UI kit принимает строки,
а domain не зависит от locale. Пользователь проверяет длинные тексты и смену
языка вручную; автоматические localization tests сейчас не добавляем.

### 9.1. Аналитика действий

Единственный контракт — [P06.1](../plan/DETAILS.md#p06-1). При review feature
проверяем явно выбранные события/владельца, общий UI hook, отсутствие дублей и
запрещённых данных, consent и no-op. Event catalog обновляется в scope задачи;
SDK не проникает в domain/UI kit. Правила целиком здесь не копируем.

## 10. API, OAuth и локальные данные

На P05 подтверждаем поддерживаемый flow и формы ответов. На последующих частях
подключаем только нужные endpoints. Не генерируем заранее клиент ко всему osu!
API и не принимаем документационные примеры за проверенные ответы сервера.

- Примеры ответов API имеют указанное происхождение и response version.
  Это документация контракта; инфраструктуру тестовых fixtures не создаём.
- Зафиксированы response version, scopes, правила ID и legacy/lazer semantics.
  Repository и decoder реализуют описанный контракт без тестовых doubles.
- Auth/session владеет токенами. Feature получает repository с настроенным
  транспортом, не читает secure storage самостоятельно.
- Refresh token обрабатывается централизованно; параллельные 401 не создают
  независимые конкурирующие обновления. Повторы ограничены и проверяются.
- Ошибка сети/сессии не заменяется случайным профилем или пустым успешным
  результатом. Причина ошибки переводится в ожидаемое состояние UI.
- Cache имеет ключ, TTL/инвалидацию, предел размера и правила смены аккаунта.
  Новую offline database добавляем только по отдельной продуктовой задаче.
- Изменение версии storage plugin или формата данных требует upgrade-сценария.
  Старые значения сохраняем или предсказуемо очищаем по описанной миграции.
  Пользователь проверяет установку поверх старой версии; fresh install этого
  сценария не заменяет.

Для текущей программы BFF исключён. Токены остаются в secure storage, secret
не попадает в Git/логи; принятый риск mobile client secret записан в плане.
Официальную страницу входа открываем через подтверждённый системный auth flow.
Не запрашиваем osu! пароль в собственном поле приложения и не предполагаем
поддержку конкретного callback/PKCE без проверки провайдера.

Ротация client secret, отзыв сессий и публикация выполняются отдельно, в
выбранное время. Они не являются скрытым побочным эффектом рефакторинга.

## 11. SDK, зависимости и native-проекты

Для платформенной части фиксируем совместимую связку Flutter/Dart, plugins,
Android tools и Xcode. Версии выбираются по матрице совместимости; точные
шаги миграции проверяются в официальных документах на момент выполнения.

- Генерируем reference shell закреплённым Flutter и сравниваем с текущим host.
  Переносим application identity, нужные capabilities и platform integrations.
- Старые native-папки сначала инвентаризируем и сохраняем. Keystore и прочие
  секреты в Git не добавляем. Сборка на новом template не подтверждает сама
  по себе возможность обновить старое приложение.
- Android P03.1 использует `applicationId = io.github.wratheus.tracksu` и Kotlin
  MainActivity. Следующий P03 checkpoint добавляет explicit namespace и согласует
  package/path/manifest/R/BuildConfig
  и современный JVM target. Не подменяем app ID новым ради naming. Собственный
  native code — Kotlin; язык Gradle scripts выбирается по template отдельно.
- Новый нейминг фиксируется картой P01.1: display name, developer brand,
  Dart packages, namespace, store ID, OAuth display/redirect и support контакты.
  Не выполнять общий replace старого имени. Новый applicationId допустим только
  как явно выбранное отдельное приложение с описанными последствиями для данных
  и обновлений; текущие ключи от этого не становятся ненужными.
- Меняем зависимости совместимыми группами. Если plugin/Flutter/Gradle
  требуют совместного изменения, оформляем это как одну техническую
  подзадачу с объяснением связи; искусственно ломать её на несобираемые части
  ради правила «одна версия за раз» не нужно.
- Редизайн, перемещение всех файлов и посторонние package upgrades не входят
  в diff платформенной совместимости.
- [DEPENDENCIES](../standards/DEPENDENCIES.md) задаёт обязательные удаления и замену их
  обязанностей. До package removal проверить imports, config, scripts и native
  resources; splash/launcher assets не удаляются вместе с генераторами.
  Navigation/icons и transport мигрируют отдельными частями. Для REST допустим
  http или Dio после решения P06, один лёгкий adapter вместо полного TSD stack.
- Major upgrade storage/audio/auth plugins требует проверки их lifecycle и
  данных даже при отсутствии compile errors. Старую небезопасную миграцию
  нельзя выпускать только потому, что новый shell запускается.
- Минимальный shell может использовать явно обозначенные demo data для проверки
  toolchain. Его запуск не считается готовностью реального login или feature.
- Dependencies/lockfiles/codegen обновляем инструментами выбранной версии.
  Не правим package caches и generated registrants как постоянное решение.
- Подавление analyzer/lint/build checks допустимо только как узкое временное
  исключение с причиной и задачей снятия. Глобально выключать проверки нельзя.
- Основа analyzer и стиля — пользовательский YAML, адаптированный в
  [CODE_STYLE](../standards/CODE_STYLE.md). На P02 подключаем единую policy для app/packages;
  новый код следует ей, старый приводим по выбранному scope. Отдельно проверяем
  flutter_lints dependency, unknown rules и конфликты вложенных configs.
  Formatter/import fixes не смешиваем с переделкой поведения, root-wide
  autofix/форматирование legacy «заодно» запрещены. До P02 template не активен.

## 12. Техническая проверка и передача пользователю

Исполнитель проверяет только необходимые для задачи технические вещи: diff,
imports, формат, analyzer и сборку. Автоматические тесты и их инфраструктура
не входят в эту проверку. Ручное функциональное/визуальное тестирование делает
пользователь, исполнитель передаёт краткий список действий и ожидаемый результат.

| Изменение | Что смотрим по коду | Что пользователь проверяет вручную |
| --- | --- | --- |
| DTO/repository | Mapping, null/unknown values, query, Failure и cache | Затронутые данные, пустые ответы, ошибки API |
| Bloc | Переходы, владельцы state, query/session guards | Load/refresh, быстрая смена фильтров, возврат |
| UI kit/экран | Границы подписок, параметры компонентов | Вид и действия, длинный текст, размер шрифта |
| Router/lifecycle | Routes, IDs, создание/закрытие владельцев | Back/tabs, сохранение контекста, callback |
| Native/plugins | Конфигурация и сборка нужной платформы | Установка, запуск, внешние интеграции |
| Storage | Формат, идемпотентность, upgrade path | Обновление поверх старого приложения и повторный вход |

Существующие ошибки analyzer/build записываем отдельно от внесённых изменений.
Не выключаем проверки всего проекта, чтобы спрятать проблему текущей части.
Сборка подтверждает компилируемость, но не успешную ручную проверку сценария.

Для каждой фактической технической проверки указываем `passed / failed /
not run / blocked` с причиной. Для поведения — `ожидает пользователя /
подтверждено пользователем / есть замечания`. Автотесты отмечены `deferred: T01`
и не становятся обязательным условием завершения текущего кода.

## 13. Как убираем широкие перестройки и частые обновления

Берём конкретный источник: setState на родителе, emit общего state, таймер,
подписку или загрузку из build. Записываем, что меняется и какие элементы
должны реагировать. Рефакторинг уменьшает область состояния и подписки.

- Локальное состояние переносим в ближайшего владельца: фильтр, кнопку,
  раскрываемую секцию, preview control. `setState` внутри маленького компонента
  допустим; запрещать его во всём приложении не нужно.
- Независимые секции получают отдельные границы обновлений. Прогресс preview
  меняет его индикатор, раскрытие секции — её содержимое, pagination — список
  и footer; шапка и Scaffold не подписаны на эти локальные значения.
- Route/container не превращается в один BlocBuilder вокруг всей страницы.
  Selector/buildWhen ограничивают область там, где данные независимы; mutable
  коллекции и неполное равенство state не должны скрывать полезные обновления.
- Выделяем настоящие widgets с ясными параметрами, а не только методы из
  длинного build. Сохраняем keys, владельцев Bloc/controllers и scroll state.
- Убираем запросы из build, повторные эквивалентные emit и лишние таймеры.
  Частые полезные события направляем только затронутому UI; задержку/debounce
  задаём по смыслу действия, а не глобально для всех изменений.
- Полный loading не заменяет экран при каждой смене локального значения:
  refresh сохраняет content, секции имеют свои loading/error states.
- Не маскируем широкое состояние добавлением RepaintBoundary или кеша повсюду.
  Сначала исправляем источник и владельца обновления.

Пример: раньше изменение `_isExpanded` в State страницы снова вызывало её build.
После выделения секции `_isExpanded` принадлежит State этой секции, родитель
передаёт ей данные и не получает событие раскрытия, если ему оно не нужно.

В отчёте показываем источник → прежнего владельца → нового владельца и
затронутое поддерево. Пользователь оценивает поведение вручную. Обязательных
DevTools traces, FPS/p95-бюджетов, бенчмарков и автоматических rebuild-тестов
в текущем процессе нет; обещаний количественного ускорения тоже нет.

## 14. Что можно делать и что требует остановки

| Можно внутри выбранной части | Нельзя делать молча |
| --- | --- |
| Читать связанные файлы, искать usages, уточнять локальный контракт | Начинать следующую часть или переносить весь проект заодно |
| Делать локальные исправления и необходимые проверки | Менять продуктовые сценарии, branding, поддерживаемые OS без записи решения |
| Извлекать компоненты, вводить DTO/adapter и заменять затронутого consumer | Протягивать legacy/HTTP/storage зависимости в новые domain/UI kit |
| Исправлять подтверждённый дефект в scope и описывать ручной сценарий | Скрывать дефект под catch-all, fallback Peppy или подавление ошибок |
| Оставлять явные границы зависимостей для дальнейшей работы | Писать/переписывать/запускать тесты, добавлять mocks/golden/test CI до выбора T01 |
| Обновлять связанные generated files/lockfiles | Редактировать caches, массово форматировать посторонний код |
| Сохранять и использовать чужие незавершённые изменения осторожно | Сбрасывать worktree, переписывать историю, стирать native-папки и данные |
| Подготовить release artifact и описание | Публиковать, сбрасывать credentials, приглашать тестеров или писать ppy без выбранного пользователем действия |

При материальном расширении scope показываем факт, почему без него нельзя
закончить текущую часть, минимальный вариант решения и цену альтернативы.
Проверки и независимую работу продолжаем. Повторно согласовывать уже принятое
решение не требуется.

Новая библиотека сама по себе не требует отдельной церемонии, если она
реализует уже выбранный способ в пределах задачи. Смена подхода к state/DI,
добавление backend, внешнего сервиса или нового хранения — архитектурное решение.

## 15. Git, временный код и завершение

- Рабочее дерево проверяется до изменений; пользовательский diff сохраняется.
  Ветки по выбранным частям именуем, например, `codex/p09-profile-summary`.
- Коммит содержит понятное изменение с относящимися к нему проверками.
  Массовое форматирование/переименование при необходимости делается отдельно.
- Локальные промежуточные checkpoints допустимы. В точке интеграции должны
  пройти заявленные gates; failed/blocked проверки не прячем за названием WIP.
- Во время перехода используем короткие ветки и общий checkpoint программы.
  Параллельное расхождение двух полных приложений не создаём.
- Удаление legacy проверяется поиском usages, imports, регистрации routes,
  assets и package dependencies. История Git хранит старую реализацию.
- После P02.1 вместе с частью обновляются README и технические документы,
  которых касается изменение, а значимые изменения попадают в Unreleased
  CHANGELOG. Новая команда, package contract, настройка, migration или breaking
  change не остаётся только в сообщении исполнителя. Для чисто внутреннего
  изменения без влияния на использование запись может не требоваться — это
  отмечается в карточке. Документация описывает фактическое состояние, не roadmap;
  дату/версию выпуска и release notes не выдумываем. Секретов в примерах нет.
- Возврат кода выполняется адресно и сохраняет посторонние изменения.
  Миграция данных, опубликованный build и ротация секретов имеют отдельный
  recovery plan; git revert не восстанавливает их автоматически.

Код передаётся со статусом `awaiting_manual_check`, когда просмотрен diff,
выполнены технические проверки по scope, обновлены документы и удалён ненужный
временный код. Пользователь подтверждает поведение — часть получает `verified`.
Допустимый временный долг имеет задачу и условие удаления. Отложенный T01
не препятствует этой передаче и не требует тестов в текущем diff.

Единственный реестр статусов — таблица ROADMAP; не заводим второй список.
Проверка `blocked` отмечается в карточке как ограничение; она не превращается
в `verified` только из-за завершения доступной части работы.

### 15.1. Планируем и выполняем небольшими коммитами

Прямое требование пользователя: безопасная последовательность коммитов,
а не большой diff всей миграции. Сейчас готовим правила; ветки/коммиты не создаём.
Первую часть и её commit plan выберем отдельно. После выбора работаем в его
границах, без согласования каждого обычного метода или переименования.

1. Перед кодом записать commit plan выбранной части: ID шага, цель, файлы/scope,
   зависимости от предыдущего, изменение поведения, проверки, документация,
   граница отката. Размер определяет понятность и обратимость, не лимит строк.
2. Один коммит — одна законченная причина изменения. Не объединять перенос
   native host, SDK upgrade, новые состояния, редизайн и auth в одном diff.
   Но interface + необходимое обновление consumers, совместимые toolchain
   изменения и соответствующие generated files/lockfile сохраняем атомарными.
3. Каждый checkpoint должен разрешать imports и сохранять доступный сценарий
   либо явно быть ещё не подключённой подготовкой. Не создавать заведомо сломанный
   промежуточный коммит ради маленького размера. Если baseline уже не собирался,
   записать это, не объявлять зелёную сборку и не добавлять скрытые регрессии.
4. Перед коммитом проверить status, относящийся diff и staged diff. Staging
   адресный: не захватывать чужие изменения, секреты и unrelated files через
   безусловный `git add .`/`git add -A`. Выполнить format/analyze/build по риску;
   автотесты по-прежнему не писать и не запускать.
5. В том же логическом изменении обновить затронутую техническую документацию
   и CHANGELOG, когда он уже введён. План/карточка отражают фактический прогресс
   с первого шага. Не откладывать всё документирование в один огромный финальный
   docs commit. Рабочий комплект в `tracksu-agent-ref` обновлять на
   каждом checkpoint и включать в адресный плановый коммит.
6. После создания коммита записать hash, проверки и остаточный долг в рабочую
   карточку/handoff. Не пытаться вписать коммиту собственный hash бесконечным
   amend. Непрошедшая ручную проверку feature остаётся awaiting_manual_check;
   наличие коммита не равно verified.
7. На checkpoint с изменением поведения передать пользователю короткий ручной
   сценарий. Подготовительные неактивные коммиты не требуют бессмысленно гонять
   весь UI. Удаление заменённого legacy и зависимого callback — после нужного
   подтверждения и проверки consumers, отдельным cleanup-коммитом.
8. Если обнаружилась новая крупная зависимость, обновить commit plan до расширения
   diff. Нельзя оправдывать разрастание тем, что «всё равно потом разобьём».
   Не squash-ить всю серию в один mega-commit без отдельного решения. Push,
   публикация и переписывание истории не следуют из разрешения на локальные шаги.

Пример для P05.1, уточняемый перед стартом, а не готовое поручение:

| Шаг | Отдельный результат | Что не входит |
| --- | --- | --- |
| C1 | Карта DI, контейнер/scope и constructors для уже существующей зависимости; старый вход работает | Все будущие сервисы и перенос экранов |
| C2 | Bootstrap и один consumer подключены к этому графу; error/retry/lifetime проверены по scope | Analytics, OAuth/session rewrite, UI redesign |
| C3 | После ручной проверки удалён заменённый путь создания зависимостей, уточнены docs | Удаление legacy других feature |

Во всех шагах документация меняется вместе с относящимся решением. Если C1/C2
невозможно безопасно отделить, меняем границу коммита заранее, а не оставляем
сломанное приложение. Точные сообщения коммитов пишем по факту; например,
`refactor(di): wire bootstrap through dependency scope` с ID части в описании.

## 16. Пример: P09.1 — шапка и статистика профиля

Это пример разбиения, не распоряжение начать реализацию.

Цель: новый путь показывает профиль по UserId/Ruleset, сохраняет content при
refresh и корректно отображает отсутствие данных/ошибки. Списки scores, карты,
новости и audio относятся к другим частям.

Вход: готовы foundation/UI kit/session; известен контракт Get User и примеры
данных. Форма профиля и ожидаемые различия согласованы.

1. Decoder и domain-модель профиля по контракту. Учесть nullable статистику,
   user/ruleset identity и ошибки обязательных данных.
2. Repository и mapping с явным запросом и Failure; presentation не получает
   JSON или access token. Mock transport и тесты не добавлять.
3. ProfileBloc: load, refresh с сохранением content, локальные статусы секций,
   защита от устаревшего ответа при смене ruleset.
4. ProfileView из UI kit и небольшой route/container. Разместить подписки у
   нужных секций, не обновлять целую страницу от локального setState/emit.
5. Переключить профильный путь, проверить diff/analyzer/сборку и передать
   пользователю сценарии: четыре ruleset, refresh/error, back/tabs, длинное имя.
6. Удалить ставшие ненужными legacy-части; сохранить те, которые ещё обслуживают
   scores/maps, с явной задачей удаления на P10.

Выход: пользователь проверяет четыре ruleset; по коду загрузка не вызывается
из build, независимые секции не подписаны на чужие локальные изменения.
Если удалённый legacy route был единственным fallback, возврат оформляется
через Git, а не бессрочным хранением второго включённого экрана.

## 18. Старт следующей сессии

Открыть [ROADMAP](../plan/ROADMAP.md). Если часть ещё не выбрана — предложить
P00 и её границы, не начинать миграцию автоматически. После выбора создать
`plan/work/<ID>.md` по шаблону раздела 17: это фактическая карточка, не копия
всего плана. Сейчас пустые карточки всех этапов не создаём.

пользователя не повышать до verified. При паузе обновить handoff в той же карточке.
