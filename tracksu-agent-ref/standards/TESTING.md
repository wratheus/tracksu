# Проверка поведения и регрессий

2026-10-03 · актуальное поручение пользователя; заменяет прежний запрет tests.

Автотесты нужны на ключевые реальные случаи, а не на каждый метод и не ради
процента покрытия. Перед добавлением теста называем конкретную поломку,
действие пользователя и однозначный ожидаемый результат. Если такой результат
нельзя надёжно проверить автоматически, выбираем проверку в симуляторе/на
устройстве и честно отмечаем её границы.

- Проверяем наблюдаемый контракт: например, refresh → ошибка → Retry сохраняет
  данные/scroll; старый ответ не заменяет новую выборку; повреждённый обязательный
  payload не становится пустым успехом; последняя ссылка доступна под overlay.
- Для исправленного бага сначала воспроизводим падение теста на прежнем коде,
  затем проверяем исправление. Для защиты уже сделанного исправления полезна
  локальная проверка, что его удаление действительно ломает тест.
- Используем реальные Bloc, DTO, router и UI-компоненты. Подменяем только
  необходимую внешнюю границу: ответ API, storage или контролируемую ошибку.
  Новые production API исключительно ради теста не добавляем.
- Тестовые данные соответствуют реальному контракту и форматированию UI.
  Нельзя сдвигать проблемный элемент, подменять сценарий или ослаблять ожидание,
  чтобы тест стал зелёным. Непрерывные animations проверяем точными pump frames.
- Нет обязательного coverage target, теста каждого getter/перевода, массовых
  golden и отдельной тестовой платформы без конкретного назначения.
- Сначала targeted tests; затем полный `fvm flutter test --no-pub`, когда это
  быстро и осмысленно. `fvm flutter analyze --no-pub` включает тесты. Новые ignores
  и ослабление analyzer ради зелёной проверки запрещены.
- Исполнитель сам работает с GUI симулятора, проверяет реальные клики,
  навигацию, media и ошибки. Записывает устройство, сценарий, фактический результат
  и блокеры. Код/debugger/build не выдаются за подтверждённый GUI или звук.
- Приёмка дизайна пользователем, физический звук/audio focus, OAuth/callback и
  реальные сетевые сбои остаются отдельными проверками, когда их не покрывает
  конкретный тест. Зелёный suite не означает 100% покрытия feature.

Рабочая карточка хранит краткую таблицу «риск → тест/GUI → результат». README,
CHANGELOG и очередь обновляются вместе с поведением. Широкая инфраструктура
T01 остаётся отдельной задачей; целевые regression tests входят в обычную работу.
